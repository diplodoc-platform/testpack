## T7.3 — Golden File Comparison (2026-09-04)

- T7.3 implements golden-file comparison for the `document-rendering` verification profile (T7.1). Three scripts, a Playwright test suite, and a CI workflow were already partially in place from a prior agent run. This iteration registered the test suite in `src/tests/index.ts`, fixed a whitespace normalization bug, created the CI workflow, and verified all 44 tests pass.
- **Three scripts** (all untracked in testpack submodule working tree, plain Node.js CJS — not compiled by esbuild since they're loaded via `require()` at runtime from the test files):
  - `scripts/build-corpus.js` (201 lines) — builds the reference document corpus at a git ref: resolves SHA, stashes uncommitted changes, checks out the ref, runs `npm ci` + `npm run docs`, copies `docs/output/` to the target dir, writes `metadata.json`, restores original working tree. Exports 9 pure helpers for testing.
  - `scripts/compare-artifacts.js` (354 lines) — compares file tree + normalized HTML + asset links between expected (base SHA) and actual (PR head SHA) corpus builds. `normalizeHtml` collapses whitespace, sorts attributes alphabetically, strips script content, normalizes style whitespace. `diffFileTree` detects added/removed/common files. `compareArtifacts` orchestrates all comparisons and returns `hasDifferences`. `renderReport` produces a markdown report with a "CODEOWNER Approval Required" section.
  - `scripts/compare-svg-dom.js` (432 lines) — compares SVG DOM structure: viewBox, element count/tags/attrs, gradient count, mask count, link count. Uses a lightweight string-based parser (`extractSvgStructure`) that extracts critical attributes (`id`, `href`, `viewBox`, `mask`, `fill`, gradient/filter/pattern/clip-path attrs) without requiring a full DOM parser. Tracks 29 critical SVG element types. `compareSvgDoms` orchestrates per-file comparison. `renderReport` includes CODEOWNER notice.
- **Whitespace normalization bug fix**: The original `normalizeHtml` used `.replace(/>\s+</g, '><')` which only strips whitespace BETWEEN tags (e.g. `<div> <p>` → `<div><p>`). But whitespace between a tag and text content (e.g. `<p> hello world </p>`) was NOT stripped — the regex only matches `>` followed by whitespace followed by `<`, so `<p> hello` has `> h` (not `> <`). Fix: replaced with two separate replaces `.replace(/>\s+/g, '>')` and `.replace(/\s+</g, '<')` which strip whitespace adjacent to tags from both sides, handling both inter-tag and tag-to-text whitespace. This makes `<div>\n  <p>  hello  world  </p>\n</div>` normalize to `<div><p>hello world</p></div>`.
- **Test suite** (`src/tests/golden-files/index.ts`, 469 lines, 44 tests): The test suite tests the pure helpers from all three scripts via `require()` (since the scripts are plain CJS JS files, not TypeScript). It does NOT require a running browser — the tests are pure unit tests that run within the Playwright runner. 5 integration tests require `docs/output/` to exist (skipped if not built). 3 CLI execution tests run the scripts as child processes via `execSync` and verify exit codes. 3 verification-profile integration tests verify the `document-rendering` profile references `corpus-build-base`, `corpus-build-head`, `artifact-compare`, `svg-dom-compare`, and `screenshot-capture` steps.

## T7.5 — Arcadia External Check (2026-09-04)

- T7.5 implements the "Arcadia External Check" — the final story in E7 (Deep Verification). Arcadia is the Yandex internal version control system (monorepo) that consumes Diplodoc packages as contrib libraries. The check verifies that Diplodoc package updates don't break downstream consumers in the Arcadia monorepo. Three deliverables: `scripts/arcadia-check.js` (dual-mode CLI + module with pure helpers, 367 lines), `src/tests/arcadia-check/index.ts` (57 Playwright unit tests), and `.github/workflows/arcadia-check.yml` (177 lines, CI workflow). - **Script design**: `scripts/arcadia-check.js` follows the exact same dual-mode pattern as `scripts/downstream-check.js` (T7.4): runnable as a CLI (`node scripts/arcadia-check.js --package transform`) and as a module exporting pure helpers for unit tests. The script resolves the Arcadia contrib path for a given Diplodoc package, resolves the Arcadia consumer projects that use the contrib library, builds and tests each consumer via `ya make` (the Arcadia build system), and renders a structured markdown report. Pure helpers exported: `parseArgs`, `ARCADIA_PACKAGES`, `ARCADIA_CONTRIB_PATHS`, `ARCADIA_CONSUMERS`, `isArcadiaPackage`, `resolveContribPath`, `resolveArcadiaConsumers`, `isArcadiaAvailable`, `resolveArcadiaRoot`, `consumerExists`, `buildArcadiaConsumer`, `runArcadiaConsumerTests`, `buildConsumerResult`, `summarizeConsumerResults`, `runArcadiaCheck`, `renderReport`, `truncate`.
- **Dry-run mode**: The `arc` CLI (Arcadia's VCS, analogous to git) is NOT available outside the Yandex intranet — the public CI runners (GitHub Actions) cannot access Arcadia. The script handles this gracefully: `isArcadiaAvailable()` checks for the `arc` CLI via `execSync('arc --version')`, and when not found, `runArcadiaCheck` automatically falls back to dry-run mode (`dryRun: true` in the result). In dry-run mode, `buildArcadiaConsumer` and `runArcadiaConsumerTests` skip actual build/test operations and just validate consumer existence. The `--dry-run` CLI flag forces dry-run mode even when `arc` is available (for testing). The report includes a "Dry-run mode" notice explaining that consumer existence is validated but no build/test operations are performed.
- **ARCADIA_PACKAGES**: The three core packages that are consumed by Arcadia: `transform`, `components`, `cli` — same set as T7.4's `CORE_PACKAGES` since these are the packages whose changes ripple to the most consumers, including external ones. `ARCADIA_CONTRIB_PATHS` maps each package to its path in the Arcadia contrib tree (`contrib/skins/diplodoc/packages/<name>`). `ARCADIA_CONSUMERS` maps each package to a list of Arcadia project paths (relative to the Arcadia root) that consume the contrib library. Consumer paths are NOT prefixed with `contrib/` (they are project paths, not contrib paths) — tests explicitly verify this. The consumer list is derived from the known Yandex internal projects that depend on Diplodoc (e.g. `cloudide/frontend`, `docs/tools`, `wiki/frontend`).
- **`ya make` build system**: Arcadia uses `ya make` (not npm) as its build system. `buildArcadiaConsumer` runs `ya make` (build only) and `runArcadiaConsumerTests` runs `ya make -t -A` (build + tests) in the consumer directory. Both have generous timeouts (600s for build, 900s for tests) since Arcadia builds can be large. In dry-run mode, these operations are skipped entirely.
- **`resolveArcadiaRoot`**: Walks up from a starting directory to find the Arcadia monorepo root, identified by the presence of a `.arc` directory or an `a.yaml` file at the root (both are Arcadia-specific markers). Walks up to 20 levels (Arcadia can have deep directory nesting). Returns null when not found (expected when running outside the Yandex intranet). The test for null uses `os.tmpdir()` (outside any Arcadia tree) following the same pattern as T7.4's `resolveMetapackageRoot` test fix.
